### Dominant Candidate: Minimal pCID Envelope

Kernel-facing working shape, expressed as CDDL-like pseudo-format:

```cddl
; Candidate shape only. Not frozen.
grid-envelope = [
  pcid: cid,      ; content hash of the protocol spec for this payload
  payload: bstr   ; exact canonical bytes interpreted only by that pCID
]
```

Receiver behavior:

| Condition | Candidate receiver action |
|---|---|
| `pcid` unsupported | Preserve exact bytes as uninterpreted evidence if policy permits; do not parse or semantically accept the payload. |
| `pcid` supported, payload invalid | Reject semantic acceptance; optionally keep a local broken-promise observation. |
| `pcid` supported, payload valid | Dispatch to the pCID handler; promise meaning, proof rules, and failure states come from that spec. |
| Payload contains nested pCIDs | Recurse only where the current pCID explicitly defines nested pCID fields. |
| Relay/store-forward path | Carriage is not acceptance. Local policy records whether Alice, Bob, or Carol carried bytes without promising their meaning. |

Strengths:

- Small enough for constrained devices and stable long-term parsers.
- Lets pCID determinism replace capability-shopping maps.
- Matches Promise Theory: autonomous agents promise behavior under a named
  protocol; receivers keep local observations about kept or broken promises.
- Allows pCID-defined payloads to evolve without changing the universal grid parse
  surface.

Weaknesses:

- The signature/proof location is not settled. It may belong inside the
  pCID-defined payload, in a pCID-specific outer wrapper, or in both.
- Unknown-pCID retention still needs quota, privacy, relay, and denial-of-service
  policy.
- Encoding is not final. CBOR is simple; DAG-CBOR remains attractive for
  canonical CAS and audit bytes.

### Candidate pCID-Owned Payload Shapes

Payloads are not universal claim cards or conformance bundles. Each payload
shape is owned by its pCID. Guide-facing wording should stay simple: "I,
Alice, promise that this payload meets the protocol specification referred to
by this pCID." The following examples show the current level of complexity the
guide should prefer unless future simulations justify more. Source: `DI-pagin`;
`DI-baral`.

#### Capability Token as Promise

Candidate payload for a pCID that means "capability token as promise":

```cddl
; Candidate payload only. Field meaning and arity are fixed by the protocol
; named by this pCID.
capability-token-promise = [
  promiser: agent-ref,          ; Alice promises behavior
  promisee: agent-ref / nil,    ; Bob, or nil for a bearer-style promise
  promise_body: bstr,           ; compact pCID-defined promise body
  constraint: bstr / nil,       ; optional expiry, scope, or redemption condition
  proof: bstr / nil             ; pCID-defined signature or witness bytes
]
```

Design rule:

- This is a promise from a promiser, not a global permission.
- The pCID defines what `promise_body`, `constraint`, and `proof` mean.
- A receiver records local kept/broken observations in promise accounting
  records; no central ledger or permission registry is implied.
- Current simulation coverage is adjacent rather than dedicated, so this should
  remain a candidate payload shape until `rozas.12` or a protocol-specific TODO
  adds a focused simulation.

#### Payload Promise Wording

Base guide sentence:

> "I, Alice, promise that this payload meets the protocol specification
> referred to by this pCID."

Design rule:

- Treat `meets` or `conforms` as a predicate about payload bytes against the
  pCID's rules, not as the name of a separate universal bundle type.
- Keep promise wording on the payload/spec relation unless a specific pCID
  defines a heavier wrapper.
- Let Alice, Bob, and Carol decide locally whether that promise was kept in
  their relationship and workload.

#### Nested Payload

Candidate shape when a pCID needs recursion:

```cddl
; Candidate payload only. The outer pcid defines that this payload contains a
; nested pCID and exact nested bytes.
nested-payload = [
  inner_pcid: cid,
  inner_payload: bstr,
  inner_proof: bstr / nil
]
```

Design rule:

- Variable arity belongs to a pCID-defined payload shape, not to the universal
  grid envelope.
- Generic peers parse only the outer `[pcid, payload]` envelope unless they
  support the protocol named by that pCID.

### Alternative Envelope Designs

| Design | Evidence | Strengths | Weaknesses |
|---|---|---|---|
| Minimal `[pcid, payload]` | Turn-157/177 notes, `SIM-kurim`, fixed-envelope family | Smallest durable parse surface; pCID determinism does the work. | Needs pCID-specific decisions for proof, unknown retention, and canonical encoding. |
| Explicit `sig_pcid` tuple | `SIM-jufag`, `SIM-bimos`, mandatory signature-payload variants | Good when generic peers must see that a proof-bearing wrapper exists. | Adds universal fields that may duplicate payload-pCID semantics. |
| Outer attestation / Multisig | `SIM-natim` | Useful for origin/relay/holder/forwarder distinctions and high-value audit paths. | Heavier than the small-device default; should remain pCID-specific unless consensus broadens. |
| Signed summary header + nested schema | `SIM-maraz` | Gives sparse peers bounded audit hooks. | Risks recreating generic promise-wrapper maps if summary fields grow. |
| pCID-defined variable arity | `SIM-sajar` | Good inside a pCID-owned payload shape. | Poor as a universal envelope rule because generic peers cannot bound parse work without pCID knowledge. |
| Hard reject unknowns | `SIM-gazan`, `SIM-dorut`, `SIM-nipoh`, `SIM-tohol` | Simple semantic safety. | Weak 100-year migration and mixed-version evidence retention. |
| Opaque store-forward | `SIM-gasus`, `SIM-hagom`, `SIM-ruzil` | Preserves future evidence. | Must be labeled as carriage only, not semantic acceptance. |

### Open Protocol Decisions

| Decision | Why it matters |
|---|---|
| Proof placement | Decide whether signatures/proofs are always pCID-defined payload fields, sometimes outer pCID-defined wrapper fields, or both. |
| Unknown-pCID policy | Retain-versus-reject behavior is still open; quota, privacy, blind-carry labeling, and relay bounds remain open. |
